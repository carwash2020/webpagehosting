# Server-side two-factor for the Workspace tools: rollout and way back in

Closes `docs/ACTION-ITEMS.md` #13 (2026-09-23 audit, finding #4, HIGH). The reasoning is in
`docs/specialist-logs/security.md` ("2026-09-25: server-side two-factor enforcement").

## What it does

Before this, only `tools/login.html` asked for the 6-digit code. Anyone with Connor's or
Steve's password could skip that page, call Supabase directly with a password-only session,
and read or change everything. They could also mint new recovery codes.

Now the server applies one rule. **If an internal account has an authenticator, only a session
that passed the authenticator (`aal2`) gets internal access.** It covers every internal table,
bucket and edge function. An account with no authenticator works exactly as before.

A single switch controls it, `public.internal_mfa_enforcement.mode`:

| mode | What happens |
|---|---|
| `log` | **Dry run.** Nothing is blocked. Everything that *would* be blocked is recorded. |
| `enforce` | Password-only sessions on accounts with an authenticator are refused. |
| `off` | The check is skipped entirely. |

Two things are on in every mode, because neither can lock anyone out:

- **New recovery codes** can only be generated by a fully verified session on an account that
  has an authenticator.
- **Deleting recovery codes** is refused for a password-only session while the authenticator exists.

**Signing in with a recovery code** now removes the old authenticator and signs out every
other device, since a lost phone may still be signed in. The login page then asks you to set
up a new authenticator right away. This path works in every mode.

## Rollout

1. **Apply the migration** (`sql/security/enforce_internal_mfa_server_side.sql`). It lands in
   `log` mode. Rehearsed first on the live data inside a rolled-back transaction.
2. **After merging, deploy the 15 edge functions from `main`.** They are advisor-health,
   create-pos-charge, delete-portal-invoice, send-contract-notification, send-invite,
   send-invoice-notification, send-job-confirmation-email, send-quote-notification,
   set-invoice-paid, sync-checkup-to-portal, sync-contract-to-portal, sync-invoice-to-portal,
   sync-job-to-portal, sync-quote-to-portal and trigger-workflow.
   - Keep `verify_jwt` on for every one.
   - Deploy only after the migration is live. Each function calls
     `check_internal_mfa_for_edge_function()` and refuses the call if it can't reach it.
   - Afterwards, probe each one with the anon key and expect **401**, as before.
   - Three of these also ship code that `main` had and live didn't:
     - delete-portal-invoice: the paid-race fix;
     - sync-job-to-portal: the delete branch;
     - trigger-workflow: already matched live; the repo was brought up to date.
3. **Steve enrolls an authenticator.** Sign out, then sign in. The login page walks you through
   it: scan the QR code, enter the code, save the recovery codes.
4. **Review window: a few days of normal use by both of you.** Run the review queries below
   once a day. A `would_block` from Steve or Connor that isn't a test you just did is the
   signal to stop and find out why.
5. **Test both accounts in `log` mode** (checklist below).
6. **Flip to `enforce`,** then run the same checklist again right away.

```sql
update public.internal_mfa_enforcement
set mode = 'enforce', changed_at = now(), note = 'Enforcing after review window'
where id;
```

## Review queries (Supabase dashboard → SQL editor)

```sql
-- 1. Edge functions, tools pages and recovery: everything the check decided.
--    In log mode, "allowed" rows prove it ran on real traffic.
select created_at, email, source, outcome, aal, session_id
from public.internal_mfa_gate_log
order by created_at desc
limit 200;

-- 2. Every current session on an internal account that has an authenticator.
--    Any row here that isn't aal2 loses internal access at the flip.
select u.email, s.id as session_id, s.aal, s.created_at, s.refreshed_at
from auth.sessions s
join auth.users u on u.id = s.user_id
where exists (select 1 from public.account_roles ar where ar.email = u.email)
  and exists (select 1 from auth.mfa_factors f where f.user_id = u.id and f.status = 'verified')
order by s.refreshed_at desc nulls last;
```

   The first entries (2026-09-25, around 17:00 UTC) are from the rollout's own checks. They
   used simulated sessions, including one password-only Connor session
   (`12c8ee0c-...`), so they are not real traffic.

3. **Direct table reads** (the RLS path) can't write rows, because they run read-only. They
   write a warning to the Postgres log instead. In the dashboard, go to **Logs → Postgres** and
   search `internal_mfa_gate`. Logs are kept for about a day, so check daily.

## Checklist: both accounts, before and after the flip

Do this on each account (Connor and Steve), once in `log` mode and again right after switching
to `enforce`. Use a normal browser window and your real phone.

1. **Normal sign-in.** Sign out, sign in with your password and your 6-digit code. The
   dashboard loads and shows your data. Open Invoices, Jobs, Clients, Settings.
2. **A write.** Save any small change (a job note, say) and reload to confirm it stuck.
3. **An edge function.** Send a test invoice email to yourself, or run a Dev Tools action.
4. **Recovery-code sign-in.** Sign out, then sign in with your password.
   1. On the code screen, choose **Use a recovery code instead** and enter one of your saved codes.
   2. Expect **"Set up a new authenticator"**. Scan the new QR code with your authenticator app,
      enter the code it shows, and save the new recovery codes.
   3. Delete the old "Triple H Workspace" entry from the app; it no longer works.
   4. You're signed in. Every other device is signed out and needs a normal sign-in.
5. **The attack itself (Connor, from a terminal).** This takes a real password-only token
   straight from Supabase, the way an attacker would, skipping the login page. The key is the
   public anon key from `tools/auth.js`.

   ```sh
   KEY='<SUPABASE_ANON_KEY from tools/auth.js>'
   URL='https://csvfqdjuobylgafgolho.supabase.co'
   read -rsp 'Password: ' PW; echo
   TOKEN=$(curl -s "$URL/auth/v1/token?grant_type=password" -H "apikey: $KEY" -H 'Content-Type: application/json' \
     -d "{\"email\":\"connor@triplehenterprisesllc.biz\",\"password\":\"$PW\"}" | python3 -c 'import sys,json;print(json.load(sys.stdin)["access_token"])')
   unset PW
   curl -s "$URL/rest/v1/invoices?select=id&limit=1" -H "apikey: $KEY" -H "Authorization: Bearer $TOKEN"; echo
   curl -s -X POST "$URL/rest/v1/rpc/generate_internal_recovery_codes" -H "apikey: $KEY" -H "Authorization: Bearer $TOKEN" \
     -H 'Content-Type: application/json' -d '{}'; echo
   ```

   - **In `log` mode:** the first call returns an invoice id (the dry run blocks nothing). It
     also leaves a `would_block` warning in the Postgres log.
   - **In `enforce` mode:** it returns `[]`.
   - **In both modes:** the second call is refused with "Sign out, then sign back in with your
     authenticator code".

   This signs in, so it adds one session. Nothing else changes.

Afterwards, look at review query 1. You should see your `allowed` rows, one
`recovery_redeemed` per recovery test, and no unexpected `would_block` or `blocked`.

## If something's wrong: the way back in

**You are never locked out of the Supabase dashboard.** It uses your supabase.com login, not
the Workspace one. From its SQL editor:

**Fast (takes effect on the next request):**

```sql
update public.internal_mfa_enforcement set mode = 'log', changed_at = now(), note = 'why' where id;
```

Use `'off'` instead of `'log'` to skip the check entirely. If the row was somehow deleted,
recreate it:

```sql
insert into public.internal_mfa_enforcement (id, mode, note) values (true, 'log', 'restored')
on conflict (id) do update set mode = excluded.mode, changed_at = now(), note = excluded.note;
```

**Full rollback:** run `sql/security/rollback_enforce_internal_mfa_server_side.sql`.
- It sets the mode to `off`.
- It restores the four replaced functions exactly as they were.
- It drops the new recovery function, and the login page falls back to the old one.
- It keeps the two functions the edge functions and pages call. With the mode `off`, both
  answer "allowed", so nothing breaks.

**Lost phone and no codes left:** remove the authenticator from the SQL editor. The next
sign-in then asks for a new one:

```sql
delete from auth.mfa_factors where user_id = (select id from auth.users where email = 'you@triplehenterprisesllc.biz');
delete from public.internal_mfa_recovery_codes where user_id = (select id from auth.users where email = 'you@triplehenterprisesllc.biz');
```

## Known limits

- **No authenticator, no protection.** This is the opt-in rule, as asked. An account that
  never enrolled, or abandoned the new-authenticator step after a recovery code, is
  password-only on the server too. The login page still forces enrollment for Owner and
  Developer permissions, but only on a fresh sign-in.
- **Tokens already handed out.** A recovery code signs other devices out. Access tokens those
  devices already hold keep working until they expire (up to an hour); they just can't be
  refreshed.
- **Portal accounts** are out of scope and unchanged.
